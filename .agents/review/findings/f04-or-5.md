# f04-or-5: Three of D3's four empty-negation operators mean the opposite at runtime

**Severity**: MEDIUM — `not_contains ""` / `not_starts_with ""` / `not_ends_with ""` match **nothing**, the inverse of "attribute is populated".
**Status**: Verified
**Branch**: — (docs-only plan amendment; no code branch)
**Commit**: `0c9e4be`

## Evidence

- `.agents/plans/F04-genuine-conversational-answers.md:167` — Slice 5 accepts all four negation operators with an empty value (`not_equals ""`, `not_contains ""`, `not_starts_with ""`, `not_ends_with ""`) as "attribute is populated".
- `csharp/Services/DirectoryPlanExecutor.cs:1486-1488` — `MatchesBaseOperator` short-circuits on an empty `expected`: `"contains" => expected.Length == 0 || …`, and identically for `starts_with` and `ends_with`. Every candidate string, including `string.Empty`, matches.
- `csharp/Services/DirectoryPlanExecutor.cs:1450-1474` — `RecordMatchesFilter` strips the `not_` prefix (`:1450-1451`), evaluates the base operator over the candidate list, then negates: `return isNegated ? !match : match` (`:1474`).
- `csharp/Services/DirectoryPlanExecutor.cs:1485` — `"equals"` has **no** empty short-circuit, so `not_equals ""` alone behaves as intended.
- `.agents/plans/F04-genuine-conversational-answers.md:169` — the specified guard exercises only `title not_equals ""`, the one operator that already works.

## Predicted observable failure

A plan carrying `title not_contains ""` over any record set: for every record `MatchesBaseOperator` returns `true` (empty needle), so `match` is `true`, so the negation returns `false`. The filter excludes **every** record and the turn yields zero rows — while the validator, per Slice 5, has accepted the plan as a valid "attribute is populated" filter. The user sees an empty result for a question that should have returned the populated subset, with no error to explain it. Slice 5's guard does not catch this because it tests only `not_equals`.

## What

Slice 5 generalizes validator *acceptance* across four operators but assumes executor *semantics* are uniform across them. They are not: three of the four have an empty-needle short-circuit that inverts under negation. Accepting a plan the executor evaluates backwards is worse than the current hard rejection — a visible error becomes a silent wrong answer. This directly violates the slice's own stated requirement at `:168` that "a plan the validator accepts must be one the executor evaluates identically".

## Approach

Amend Slice 5: route **every** empty-value negation through one explicit populated-attribute predicate evaluated *before* generic operator dispatch, rather than letting it fall through to `MatchesBaseOperator`'s per-operator string logic. One predicate — "the attribute has at least one non-null, non-whitespace value" — serves all four operators, which is both correct and simpler than patching three short-circuits. Widen the guard to cover all four operators across missing, blank, whitespace-only, populated, and multivalued attributes.

## Files changed

- `.agents/plans/F04-genuine-conversational-answers.md:167-169` — Slice 5 specifies the single populated-attribute predicate ahead of operator dispatch, and the guard is widened to all four operators and the attribute-shape matrix.

## Guard proof

Docs-only amendment to an unimplemented plan; no code guard applies. The amended guard is specified in the slice: `not_contains ""`, `not_starts_with ""`, and `not_ends_with ""` must each return the populated subset (not the empty set), proven to fail against `MatchesBaseOperator`'s empty short-circuit at `:1486-1488`. The pre-existing single-operator guard would have passed while three of four operators were broken — that vacuity is the reason this finding is admitted rather than deferred.
