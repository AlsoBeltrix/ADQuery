# f06s2-cr-2: The reverse synonym lookup drops advertised spellings when an attribute has three

**Severity**: MEDIUM — on a deployment using the hardcoded fallback allow-list, a model
following the prompt is refused for a spelling the prompt says works.
**Status**: Fixed
**Branch**: — (repo policy: commit on `master`, one finding per commit)
**Commit**: `<filled in after commit>`

## Evidence
Recorded as the reviewer stated it:

> Both prompts advertise `sn`/`Surname` as interchangeable at
> `csharp/Configuration/prompt_template.txt:28` and `csharp/Services/ClaudeService.cs:487`. The
> map does not contain `sn -> Surname`; it contains `surname -> Surname` at
> `csharp/Security/DirectorySecurityPolicy.cs:61`, and the reverse dictionary picks that value
> at `csharp/Security/DirectorySecurityPolicy.cs:82-87`. The hardcoded fallback User list
> contains `sn` at `csharp/Security/DirectorySecurityPolicy.cs:204` but not `surname` or
> `Surname`.

## Predicted observable failure
> If the configured User allow-list file is missing and the service falls back to defaults, a
> model following the new prompt can emit `Surname` and validation will reject it even though
> `sn` is allowed and the prompt says the pair works. The user sees the original class of
> validation failure on the fallback deployment path.

## What actually went wrong, generalized
The map was one-to-one and the reverse was derived by `GroupBy(...).First()`. That is sound
only while every attribute has exactly two spellings. `Surname` has three (`sn`, `surname`,
`Surname`) and `Country` has three (`c`, `co`, `Country`), so the reverse lookup collapsed each
to one arbitrary partner and silently dropped the rest — including, for `Surname`, the very
spelling the prompt advertises.

The `EveryPairThePromptAdvertises_ActuallyResolves` guard I wrote in Slice 2 did not catch it
because it runs against the allow-list **files**, which carry both `sn` and `Surname`. The gap
was only reachable on the hardcoded fallback path, which no test exercised.

## Approach
Synonyms are now **equivalence classes**: every spelling maps to the full set of spellings for
its attribute, and a request is allowed when *any* member of the class is on the object type's
list. This removes the direction question rather than patching one direction, so a third or
fourth spelling cannot reintroduce the same gap.

The security property is unchanged and still holds by construction: every member of a class
names the same directory attribute, so admitting a request grants exactly the access the list
already granted under a different spelling. `ASynonymNeverWidensTheAllowList` and the new
`TheFallbackAllowList_StillRefusesWhatItAlwaysRefused` both assert it.

An explicit `sn -> Surname` entry was added as well, so the class is complete rather than
relying on `surname` to bridge it.

## Guard proof
`TheFallbackAllowList_AcceptsEveryAdvertisedSpelling` over `Surname`, `surname`, and `sn`,
driving a policy with **no configured files** so the hardcoded fallback is exercised — the path
the finding names and the one nothing previously covered. Reverting
`DirectorySecurityPolicy.cs` reddens it.
