# f04-or-6: The 32 KB backstop is smaller than a valid bounded question history

**Severity**: HIGH — the "unreachable" error path is reachable by ordinary in-bounds input, so the backstop becomes the shaper the owner ruled it must not be.
**Status**: Verified
**Branch**: — (docs-only plan amendment; no code branch)
**Commit**: `0c9e4be`

## Evidence

- `.agents/plans/F04-genuine-conversational-answers.md:211` (Slice 6, "Byte cap as backstop") — `FollowUp:MaxContextBytes` becomes 32 KB, "far above the ~6 KB worst case, so it never shapes a normal turn," and tripping it is treated as a misconfiguration.
- The ~6 KB figure is derived from two measured samples: value slice top-20 = 232 bytes (job `173508149`) and prior question + plan summary = 195 bytes (job `173901220`), extrapolated as "~100 bytes per question" across 50 questions.
- `csharp/Controllers/QueryController.cs:1329` — `[Required] [StringLength(1000, MinimumLength = 1)]` on `QueryRequest.Query`. A single question may legitimately carry **1,000 UTF-16 code units**, not ~100 bytes.
- UTF-8 encoding: 1,000 ASCII code units = 1,000 bytes; 1,000 non-BMP code units = 500 astral characters = 2,000 bytes.

## Predicted observable failure

33 maximum-length ASCII questions (33 × 1,000 = 33,000 bytes) exceed the 32 KB backstop before the fixed components are added. With non-BMP text roughly nine questions suffice (9 × 2,000 = 18,000, and ~16 reach 32 KB). A user asking long, detailed questions — precisely the conversational use F04 exists to serve — trips the "this should never happen" logged-error path with entirely in-bounds input. Depending on how the error is handled, the turn either fails or loses its conversational context. The byte cap is then doing exactly the shaping the owner rejected.

## What

The worst case was extrapolated from observed short questions rather than computed from the enforced per-question bound. The component-bounds design (F04-D6 part 2) is sound, but its arithmetic must be driven by each component's *maximum*, not its *sample*. Two knobs — `MaxPriorQuestions` and `MaxContextBytes` — were chosen independently, so nothing guarantees the second exceeds what the first permits, and the plan's central claim ("it never shapes a normal turn") is unproven rather than false-by-construction.

## Approach

Amend Slice 6 so the relationship between the knobs is an enforced invariant, not an estimate. Compute the worst case from the enforced bounds: `MaxPriorQuestions × maxQuestionBytes` (where `maxQuestionBytes` derives from the `QueryRequest.Query` `[StringLength]`, at 2 bytes/code-unit for non-BMP safety, so 2,000 bytes per question) plus the fixed-component maxima (value slice at `SummaryRowCount` buckets, plan summary, distribution summary). Startup-validate that `MaxContextBytes` exceeds that sum, in the same reconciliation style `FollowUpOptionsValidator` already uses for the transport guard — so a misconfigured pair fails at boot rather than mid-conversation. State the chosen `MaxPriorQuestions` and the resulting derived floor explicitly.

## Coder dispute (if any)

None. The finding is correct and identifies unmeasured-typical-usage reasoning: the coder extrapolated a worst case from two short samples while an enforced per-question maximum was available in the code. The coder had noted the sample was thin (n=1 per component) but did not act on it.

## Known gaps

The exact `MaxPriorQuestions` value is left to implementation, constrained by the invariant rather than chosen freely. Whether `maxQuestionBytes` uses 2 bytes/code-unit (non-BMP worst case) or 3 (the true UTF-8 maximum for a BMP code unit) is settled here as 2 for surrogate-pair text; an implementation may choose 3 for absolute safety at the cost of a larger derived floor.
