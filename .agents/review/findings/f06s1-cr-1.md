# f06s1-cr-1: The constraint line flattens OR groups into simultaneous requirements

**Severity**: MEDIUM — a zero from an alternatives search is explained as demanding every
alternative at once, so the user corrects the wrong constraint.
**Status**: Fixed
**Branch**: — (repo policy: commit on `master`, one finding per commit)

## Evidence
Recorded as the reviewer stated it:

> `csharp/Services/AnswerReductionBuilder.cs:294-297` recurses into child `Conditions` and
> continues, discarding the parent filter `Operator`, then
> `csharp/Services/AnswerReductionBuilder.cs:263` joins the leaves as a flat semicolon list.
> The executor treats that same operator as meaningful:
> `csharp/Services/DirectoryPlanExecutor.cs:1457-1463` and
> `csharp/Services/ActiveDirectoryService.cs:480-486` branch on "or" versus "and".

Verified against the code before admitting. The old `CollectClauses` did exactly that: on a
group node it recursed and `continue`d, so the operator was read nowhere.

## Predicted observable failure
> For a zero-row plan that searched alternatives, such as displayName equals one spelling OR
> userPrincipalName equals another, the CONSTRAINTS APPLIED line sent to Narrate has no
> indication that the clauses were alternatives. The user-visible answer will present or imply
> simultaneous requirements, so the user sees the wrong explanation for the zero and may
> correct the wrong constraint.

## Why this matters more than its severity suggests
The whole point of Slice 1 is that an empty result must be *explainable*. A flattened OR does
not merely omit information — it asserts something false about what the engine required. A
wrong explanation for a zero is worse than no explanation, because the user acts on it. The
finding lands squarely on the feature's reason for existing, which is why it was admitted
without argument despite being reported as MEDIUM.

## Approach
`RenderFilters`/`RenderFilter` replace the flattening `CollectClauses`. A group renders as
`any of (…)` when its operator is `or` and `all of (…)` otherwise, recursively, so nesting
survives. A single-child `all of` collapses to the child itself, keeping the common case
readable. Sibling filters at the top level are conjunctive, matching the executor.

The clause budget moved from a post-hoc `Take` to a `ref int` threaded through the recursion,
because a tree cannot be truncated correctly after flattening — the old code counted leaves it
had already rendered. The budget is shared across steps so the whole line stays inside the byte
accounting rather than each step getting its own cap.

## Guard proof

`AnAndGroup_IsStillReportedAsSimultaneousRequirements` — the second is the over-correction
guard, since rendering everything as `any of` would understate the Chelmsford plan's real
requirements. Both **failed against the pre-fix builder** and pass after.
`pwsh -NoLogo -NoProfile -File scripts/verify.ps1` — 383 tests, 0 warnings, both published
smokes, audit clean.
