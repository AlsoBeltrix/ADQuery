# f06s2-cr-1: Aggregation fields are validated against User regardless of the row step's type

**Severity**: HIGH — an authorization check reads the wrong allow-list, so a plan can group
rows of one object type on an attribute permitted only for another.
**Status**: Fixed
**Branch**: — (repo policy: commit on `master`, one finding per commit)
**Commit**: `<filled in after commit>`

## Evidence
Recorded as the reviewer stated it:

> `csharp/Security/PlanValidator.cs:396-402` validates every aggregation `group_by` field
> against `DirectoryObjectType.User`. The new synonym path in
> `csharp/Security/DirectorySecurityPolicy.cs:50` and
> `csharp/Security/DirectorySecurityPolicy.cs:120` makes User attribute `l` allowed whenever
> User has `City`. Computer allow-list entries in
> `csharp/Configuration/comp_allow_attr.txt:1-54` do not include `City` or `l`.

Verified before admitting. The validator's own comment said *"assume User type for aggregation
fields"*, and the Computer list has 54 entries with neither `City` nor `l` among them.

## Predicted observable failure
> A Computer plan with a valid Computer search step and aggregation `group_by ["l"]` now passes
> validation. Before this change it was refused because `l` was absent from the User list; after
> the synonym map it is accepted through `User.City` even though Computer does not allow that
> attribute. The operator sees a successful grouped query, likely one `(empty)` bucket, instead
> of the required allow-list refusal for the Computer row type.

## Admission, with a correction to the finding's framing
Admitted as HIGH: an authorization boundary that consults the wrong list is exactly the kind of
defect severity is reserved for, and my Slice 2 change is what made `l` reachable.

One correction, which the fix reflects and which does not soften the finding. **The hole
pre-dates Slice 2.** The hardcoded-User assumption meant a Computer plan could already group on
`City` — the display name — before any synonym existed. Slice 2 widened an existing hole rather
than opening one. That distinction matters only for the fix's scope: closing it for `l` alone
would have left the original defect in place, so the guard covers both spellings and
`AComputerPlan_CannotGroupOnAUserOnlyAttribute` is a `[Theory]` over `l` and `City`.

This is also the finding that justifies the review round. A boundary change needs someone
looking for how it interacts with code it did not touch, and this interaction is one I did not
consider.

## Approach
`ResolveRowStepType` resolves `projection.row_step` through the existing step lookup and returns
that step's `TargetType`; `ValidateAggregation` takes it as a parameter and checks against it.
The fallback to `User` for an unresolvable row step preserves prior behaviour for malformed
plans, which other validation rejects on their own terms. The error message now names the
object type, so a refusal says which list refused it.
